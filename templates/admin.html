Auth

Zerto 10 appliances: username + password works (Keycloak, scope=openid is handled), but the better option is a Keycloak initial access token, because then no password is stored at all. In the ZVM's Keycloak (https://<zvm>/auth/admin, realm zerto) go to Clients → Client registration → Initial access token → Create (count 1, a few minutes' expiry), copy the long token from the dialog that appears once, and paste it as the secret. The monitor spends it registering its own API client and keeps only that client's id and secret, encrypted; removing the source deletes the client again. Zerto 10.9 gives the new client read access by itself. If a ZVM refuses it, the source card names the one role to grant ({{ viewer_role }}). Opening the Keycloak console by IP while adding the ZVM by name is fine: the monitor checks they're the same server. Legacy Windows ZVMs on 9669 and the ZCM on 9989 are auto-detected.

Changes to Zerto

The monitor is read-only on every ZVM unless an admin allows a kind of change below and arms the site. Changes use the source's own credential, over the pinned certificate, once the ZVM's Keycloak grants it the rights. Each kind of change uses a client that can make only that one kind of request; polling can make none. Backups need none of this: they read Zerto's own daily VPG-settings exports.

Privileges the source's credential needs in the ZVM's Keycloak: ManageVRA for resizes, VPG management for restores and fresh exports, recovery-plan management for plans. Grant only what you allow here.

VRA resizing

Resizing a VRA through its ZVM is a planned replication outage. Zerto powers the VRA off, every VPG on it stops replicating, and a sync follows. So the monitor is read-only on a ZVM until all of the following are in place: the switch below, the site armed, a pinned TLS certificate, and the hosts' connection method recorded as public key (VIB). Changes use the source's own credential, which Zerto must grant the right privilege (ManageVRA for resizes); the roles it actually holds are shown per site below. Engineers can preview a resize; only an admin can start one. It is sent once, one at a time, with a 30-minute cooldown, 24 hours apart until five have succeeded, and at most 4 a day per site. Anything but a clean finish halts resizing until an admin acknowledges it.

Alerting

Each zORG is judged by its worst VPG, against two clocks: how long it has been continuously failing, and how long continuously not healthy. A rule fires failure once the first passes its error threshold, and warning once the second passes its warning threshold, so a zORG flapping between the two can't keep resetting its own timer. You're told when the level rises, reminded while it holds, and told once when it recovers. Email is one digest per recipient per poll; each event is also one SNMP trap. A ZVM that stops answering is alerted the same way, as [source] name.

A VPG is ignored by code only when every live alert on it has an ignored code and its replication is otherwise healthy, so an RPO breach, a sync problem or any other alert still raises it. It stays visible with an "ignored: CODE (global)" badge, and drops out of the counts, the alert emails and the SNMP figures. Admins only.

An ignore takes a VPG (or a whole zORG) out of the attention counts, alerting and SNMP failure/warning figures - it stays visible, badged. "Current problems" ignores lift by themselves the moment anything new or worse happens (another alert code, an RPO breach, a higher Zerto alert level), so they can't hide a fresh problem. Expired ignores are kept here for 30 days, then purged.

Polling & storage

Pages read the latest snapshot from SQLite (WAL) — they never poll a ZVM on load. Scrub checkpoints the WAL and VACUUMs with secure_delete so rotated or removed secrets are physically zeroed on disk (also runs automatically after credential migrations). Each poll also appends a compact history row (counts only) for the "vs 24h ago" trend and /api/history. Credentials at rest: source usernames and secrets, Keycloak registration tokens, the SMTP password, SNMP communities and the Entra client secret are Fernet-encrypted; admin passwords are bcrypt hashes.
